# 中断、记录损坏与恢复

恢复时先保全现场，再确认哪些事实可信、哪些操作已经发生。数据库、约定文件和维护对象分别处理，按实际源与目标决定下一步。

运行失败直接抛异常，以非零状态退出；stderr 的 traceback 保留原始错误与调用位置。先修正命令、权限、输入或解析问题，再重新执行。巡检失败保留上次已提交状态；维护可能已发生外部副作用，按操作记录与实际对象核对。

## 状态损坏：先修复可信记录

发现损坏后保留原状态，暂停新维护。在工作副本中定位数据库、JSON 或字段错误，对照可信备份与实际对象修复；无法确认时，由负责人恢复可信备份。数据库不可读时，同时保留其 journal、wal、shm 等实际存在的伴随文件。修复候选先通过完整性检查和相关只读查询，再恢复巡检与维护。

本机指导副本缺失时，先查部署路径与 `adaptation.json` 的裁剪记录，按已确认的版本和裁剪结果恢复指导，再继续相关维护。

各命令校验实际读取的状态：`patrol`、`resolve` 读完整 current；`status` 和目录摘要调查只读所需字段。基线损坏会阻断巡检，其他可读字段仍可用于诊断。数据库本身健康时，档案查询与不依赖 current 的服务调查也可帮助核对事实。数据库损坏或结构版本不受支持时，先处理数据库恢复，维护暂停条件继续有效。

### 读取与兼容边界

current 与 operations 数据集使用统一 reader 校验结构、字段类型、重复 key/ID、有限数字和 quarantine 身份。参与时间计算的 Unix 秒限定在 ±10¹²；无效记录在动作前阻断，并保留原状态。

### 续扫进度损坏与显式重置

`current.json.scan_progress` 损坏（例如待扫队列为空、记录字段非法）时，常规 `patrol` 会在动作前阻断并保留原状态，报错会指向显式重置入口。`status` 只读取版本、目录索引、变化、覆盖与缺口等所需字段，不校验 `scan_progress`，因此不会因进度损坏而阻断，但也不会报告该进度。该入口在巡检锁内只移除 `scan_progress`，随后按常规 reader 校验其余字段并按本轮预算重新扫描；`baselines`、变化历史、采样与待办保持不变。入口先移除进度再校验其余字段：若 current 其他部分也已损坏，进度可能已被清除而巡检仍因其他错误阻断，此时先按可信副本核对，不要重复丢弃。

需要显式重置时：

```sh
python3 /skill目录/tools/steward.py patrol --state /本机状态 --discard-scan-progress
```

只在进度确实无法接续时使用。容量不足、预算过小或目录暂时不可见不是丢弃进度的理由，先按实际原因处理；容量不足时重置也会停止并保留原进度。执行后核对 `baselines` 未变，`coverage_scope` 中的 `resumable` 从新的 pass 继续。

旧 v1 缺少可选字段时按兼容规则读取；未知 current 顶层字段予以保留，未知 operation kind 作为不可执行的历史证据保存。JSON 到 SQLite 使用显式迁移；数据库未知版本或状态丢失需先明确恢复方案，当前工具 尚无自动修复能力。

约定、旧状态 JSON、资源定义和目录说明只读取限额内的普通文件；链接、FIFO、目录、设备、超限文件或读取期间元数据变化都会使读取停止。数据库与伴随文件也要求普通文件，单条记录和整个数据集分别按预算读取，SQLite 负责页结构与事务恢复。写入要求初始化时采用的 DELETE 日志模式；配置被外部改动时先核对，工具不会静默切换模式。锁文件同样要求普通文件，锁被占用时本轮退出，保留正在使用的锁。普通磁盘 I/O 仍受系统实际响应时间影响。

## 迁移中断与数据库恢复

`migrate` 默认预览，`--apply` 才发布数据库。迁移保留旧 JSON，在 `.sqlite-migrating` 中校验导入结果，再写入 `sqlite-migration.json` 凭据并发布 `steward.sqlite3`。

- 正式库存在且完整时，以正式库为准。再次执行 `migrate --apply` 可清理与正式库指向同一对象的迁移临时名称；不匹配的残留保留供核对。
- 正式库尚未发布，但凭据、临时库和旧输入摘要一致时，可再次执行迁移完成发布。
- 只有临时库而没有发布凭据时，核对输入与失败原因；确认后可删除该临时库重试。容量不足会在发布前停止，旧 JSON 保持原样。
- 正式库丢失，且没有能由凭据核对的临时库时，恢复可信数据库备份。保留的旧 JSON 是迁移时的快照，不能代表切换后的新记录。
- 核对迁移结果并取得备份后，旧 JSON 与凭据可一同清理，释放状态预算；正式库保留。

数据库可读时用 `backup` 取得一致快照（备份写在状态区外，只核对目标目录空间），命令见[接管指导](../setup.md#旧状态迁移与导出)。恢复前暂停使用该状态的调用，在工作副本中核对备份的完整性、结构版本、本机约定和未完成操作，再安排替换。数据库提交不包含外部文件移动：即使库已恢复，操作证据仍需与实际源、目标逐项核对。

## 配置与结构升级中断

`upgrade --apply --backup /外部目录/本次升级备份` 在任何结构变更前保存原始配置、数据库一致快照与 `upgrade.json`，用独立连接核对。出现 `upgrade_incomplete` 时，stderr 先给出阶段、备份位置、schema 2 是否已确认和配置发布状态，再抛出原始异常；`schema_2_confirmed=false` 只表示尚未确认，不能据此断定完全未执行。

先保全当前状态并暂停采集与维护，独立查看 `PRAGMA user_version`、`host.json.version` 和 manifest：

- schema 升级事务失败时旧数据集保留；先处理容量、结构或 I/O 原因。
- schema 2 配置 v1 仍可由新工具读取。核对备份后重新预览；再次执行需新的备份目录，不覆盖已有恢复材料。
- 配置发布或最终读回失败时，配置可能已经替换；先核对当前字节和版本，不自动覆盖外部改写，也不盲目恢复原配置。
- schema 2 不能交回旧工具直接运行。需要回退时先处理升级后的新样本、档案和操作证据，在工作副本核对完整性及实际对象后再安排切换。

正常命令和备份边界见[接管指导](../setup.md#配置与结构显式升级)。

## 常驻采集中断与恢复

`collect` 由宿主管理生命周期：正常停止用 SIGTERM/SIGINT，采集器在批次边界收尾并留下 open 的 `collector_stopped` 缺口，下次启动把它关闭。进程被强杀（SIGKILL、断电）时不做收尾，重启后以 `unclean_stop` 缺口记录该区间；未关闭的运行在 `status` 中按心跳年龄显示为 `stale`，不冒充运行中。缺口只说明未采集区间，不推断主机状态。

`host.json` 损坏或校验失败时采集暂停并持续心跳（`config_invalid`、`config_error` 缺口）；此间 `samples`/`status` 仍可按最后有效运行的归档预算读取历史并报告当前配置错误，但采集、维护与升级不会使用该归档预算。修复配置后采集在批次边界恢复，新运行记 `config_recovered`；改配置则在边界切换并记 `config_changed`，旧配置启动的样本不冒充新配置结果。

采集运行中 `upgrade --apply` 会被 `.collector.lock` 拒绝；先停止采集再升级。常驻历史损坏时按上节数据库恢复流程处理，资源历史表随备份一并保存。

## 初始化失败：核对残留后重试

正常初始化见 [首次接管](../setup.md)。已有状态缺少 `host.json` 时，先恢复原约定。

`init` 只接受新建或空状态目录，已有普通 `.lock` 可保留。它预检全部内容、独占写入，并最后提交 host。失败时只移除本次创建且身份与内容仍匹配的文件，再清理本次创建的空目录；锁和已改变的内容保留。

回滚遇到读取、删除或身份核对错误时立即抛出，保留尚未清理的内容，异常链同时显示原始初始化失败。确认回滚完成、目录只剩锁文件后，才可重试初始化；有残留时先逐项核对。

状态目录及其后代由内部状态流程管理，始终排除在普通维护与 `restore` 目标之外。误移动的状态文件应走可信状态恢复路径，保留托管路径保护。

## 中断操作：先观察，再决定续作

Steward 维护用 `export --dataset operations` 找到操作编号，核对记录中的身份和实际源、目标。宿主工具留下的未完成动作按本机既有记录和恢复办法核实。这两类操作都先查现场，再决定续作。Steward 的操作状态如下：

| 状态 | 如何处理 |
| --- | --- |
| `planned` / `failed` | 检查副作用实际进行到哪里，保留证据后决定后续方案。 |
| `quarantined` | 已验证文件移入待回收区，且恢复依据完整；可以进入恢复预览。 |
| `restoring` | 对照两处对象与记录身份，满足恢复条件时显式续作。 |

目录或文件身份改变时，暂停该对象的恢复，交负责人判断。当前工具 没有通用 abandon/reconcile 命令，planned/failed 也不能由 restore 重放。

### 恢复文件

```sh
python3 /skill目录/tools/steward.py restore --state /本机状态 --operation 操作编号
```

恢复默认预览。本机约定仍允许、目录身份和路径相符、原位置为空时，才可加 `--apply`。恢复路径要求无符号链接的规范绝对路径；旧证据可以读回，非规范路径需先明确迁移方案。原位置已有新对象时保留该对象，停止恢复。

`restoring` 支持在身份精确匹配时继续：原位置为空就恢复文件；原位置与待回收对象均匹配时完成剩余步骤；文件已恢复且待回收对象已移除时只完成记录。其他组合保留现场，另行核对。

完成后核对身份、大小、修改时间和源目标位置。文件恢复结果先记为 restored，再清理空操作目录；清理失败直接抛出，此时按已保存的 restored 记录与实际文件判断恢复结果。

## 容量和约定在中途变化

先查看 `capacity` 的数据库可写上限与余量、普通记录、未完成操作和当前预算。写入被拒时工具保留上次已提交状态并说明占用；巡检在取得写入锁后整体提交，容量不足会回滚本轮，续扫进度与上次基线不变，下一轮从同一进度重试并报告同一原因。核对采集范围、记录保留与本机 `total_bytes` 后再决定后续，`total_bytes` 是本机约定，调整前按接管约定确认。工具在文件变更前先写入计划记录；达到 `operation_records` 上限时暂停新增。已验证的目录说明记录与已恢复的回收记录可按工具规则淘汰，未终结证据继续保留。数据库文件不会因记录减少而自动缩小，但上限内的空间会被复用；需要压缩文件时另行安排。需要调整预算或收敛普通历史时，按具体容量问题处理。

命令在锁内刷新本机约定，patrol 提交前与维护副作用前再次核对语义。约定变化时撤下旧计划，保留已有 planned/restoring 证据，重新观察后再形成计划。工具将未完成操作留给显式恢复，下一轮先核对现场。
