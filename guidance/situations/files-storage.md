# 文件、目录体积与收纳

发现目录增长、文件变化或需要整理资料时，先看本机目录规则、相关 `AGENTS.md` 和 [资源档案](../inventory.md)，弄清用途、使用者与依赖，再选择检查范围。配置、使用者或目录身份改变后，复核原有结论。

## 先看变化覆盖了哪里

当前工具按目录汇总新增、消失、移动、修改和体积差，目录增删只记一次。日常比较使用元数据，内容按调查需要另查。报告应带上测量时间、统计口径和覆盖情况。

比较前查看 `coverage_scope`。每个 root 的 `max_depth`、单层排除名称、相对 `exclude_paths`、状态排除路径、根设备与跨卷边界共同决定范围是否可比。范围改变，或旧基线缺少 scope／scope 版本不同时，本轮记录 comparison_gaps 并重建基线，暂停该范围的普通删除、体积差和增长判断。v1 基线使用 `scan_depth` 与顶层排除项，v2 使用逐 root 规则；同一轮只使用当前配置版本的规则。

`coverage_complete` 表示当前声明范围的元数据快照完整。深度边界是用户声明的范围边界：到达 `max_depth` 后不再进入更深目录，边界目录以零字节条目记录，不把未采集子树的体积计入总量，也不产生扫描缺口。排除路径和其他卷的状态仍需另查。跨卷边界只保存有限样例与截断标志。扫描不完整时保留上次完整基线；多个 root 共用同一轮的条目与时间预算，未完成的 pass 把候选记录与待扫目录保存在 `scan_progress`，按目录游标跨轮推进并在多个 root 间公平轮转。同一目录在 pass 内 mtime 变化时首次仍从头重扫，持续变化则改为从游标续扫并记录覆盖缺口，避免每轮重启；带 mtime 覆盖缺口的 pass 不更新基线、不参与删除判断，清空进度后下一轮从头复核，停止写入后即可完成。只有完整走完且没有覆盖缺口的 pass 才更新基线并参与删除判断；未扫完的范围在 `coverage_scope` 中带有 `resumable` 进度与缺口，不产生未经证实的删除。退役 root 移出活动基线，重新纳入时建立新基线；旧变化保留为历史，相关待办另行核实并关闭。

缺口按观察阶段区分：

- `patrol.gaps`（状态与 `status` 中的 `coverage_gaps`）：本轮达到时间或条目预算，或已配置 root 明确不存在、不可访问或不再是目录，扫描不完整。保留原始原因与空设备 scope，后续按需补查该范围；缺失 root 不产生未证实的删除，也不阻止 CPU、内存等其他主机观察。达到已声明的 `max_depth` 不属于这类缺口。排队目录在扫描期间消失时记缺口、清掉该子树候选并继续本轮；队列耗尽后清空进度，下一轮从头核实，不把未核实范围当作删除。同一目录 mtime 持续变化导致从游标续扫时记覆盖缺口，该 pass 耗尽后按不完整处理、不更新基线，下一轮从头复核。目录身份替换仍从头重扫。其他目录的权限或读取异常、扫描期间非根目录或挂载变化直接抛出，停止本轮并保留上次状态。
- `comparison_gaps`：当前快照完整，但根身份、观察范围或 scope 版本改变，或缺少 birth 信息使移动配对不确定。根身份与范围变化同时列入 `new_baselines`，完整快照已成为下一轮基线；移动不确定时保留两端变化，后续按任务需要调查。上一轮已有比较缺口时，本轮扫描不完整会保留这些原因；只有重新取得完整且可比的快照后才清理。
- `observation_gaps`：整机观测或原生事件历史的缺口，与目录扫描分别核对。

已确认的同路径对象替换保存在 `changes`，以 `identity_changed` 样本与 `continuity_gap` 标明，不重复计入上述缺口。缺口说明证据边界，agent 结合受影响范围、原因和当前任务判断是否需要处理或通知。升级前状态里的 `coverage_gaps` 可能仍混有比较原因；下一次成功巡检会按新语义保存。

### 平台事件与游标

- **macOS**：FSEvents 提供变化线索，有界快照负责核对当前状态。首次基线或有效历史配合所有 roots 的完整快照，才提交新游标；快照因预算未扫全时保留旧位置。事件子进程执行失败或超时按 `unavailable` 记录并继续全量扫描，返回内容无法解析时直接抛出。系统明确报告历史失效时记录该事实，下一轮重新建立基线。
- **Linux**：当前只有快照比较，两次快照之间的中间事件列为历史缺口。
- **待复核范围**：事件路径先归一为观察范围内最近的可扫描目录，同一路径或子树的重复线索合并为一项，保存首次、最近时间与次数。FSEvents 线索同时保存稳定事件 id；游标未推进时同一事件重放不刷新复核身份，只有新事件才推进；复核子树仍有排队项时，新事件只记入 `recheck_pending` 并保留目录游标；完成时按扫描起点结算，pending 更大则不判 covered，保留条目到下一轮重扫。持续写入且每轮都有新事件的复核子树会保持未完成、不更新基线，待写入停止后才收敛；这是保守选择，不冒充已确认完整。旧版浮点时间 token 按 0 处理，避免较小的事件 id 被误判为已覆盖。队列保存在 `current.event_recheck`，上限 64 项；超过上限向父目录聚合，并以 `truncated`、`aggregated` 标明截断，路径线索自身的条数或字节截断另记 `source_truncated`。下一轮续扫优先复核这些子树，复核仍由完整 pass 的 `compare` 判定变化；事件本身不生成 `changes`。完整 pass 覆盖整个 root，或未完成 pass 已复核相应子树后，对应条目从队列移除。
- **退化**：历史失效（`history_invalid`）或监听重建（已有游标后回到基线模式）时清空队列，并分别记录事件缺口 `history_invalid`、`baseline_rebuild`。线索不可用（`unavailable`）、游标待定（`cursor_pending`）或历史不完整（`history_incomplete`）时保留已确认的旧线索，在 `event_recheck.degraded` 标明原因；没有事件来源的 Linux 快照模式不使用旧队列，标记 `snapshot_only`。这些情况都退回正常全量扫描节奏，不宣称事件覆盖完整。`coverage_scope` 中的 `event_recheck` 汇总请求、已复核、仍待复核与跳过数量。

事件与快照一起解释观察结果。它们用于定位变化，文件内容和恢复能力需要各自验证。待复核队列损坏时巡检在读取阶段阻断，保留原状态；可用 `patrol --discard-event-recheck` 在锁内清除队列后重建，续扫进度与基线不受影响。

### 身份与体积怎样解释

同路径的 ID、类型或可取得的 birth 更换，记录为 `identity_changed` 修改，所属变化带 `continuity_gap`。跨路径移动只有在 ID 与类型配对唯一、两侧 birth 可取得且相同时才确认为 moved；birth 缺失时记录端点变化，并在 `comparison_gaps` 中附上 `move uncertain` 原因。没有 birth time 的平台把移动保守记为新增+删除并给出 `identity: move uncertain` 缺口，不冒充已确认移动；两个端点路径仍出现在变化样本中。跨 roots 的移动配对仍有覆盖限制。

身份不连续的净体积差带 `continuity_gap`，留作变化事实，增长速率和增长待办只使用连续样本。可靠移动跨越目录边界时，受影响目录与祖先带 `migration_delta`，迁入量单独解释；包含移动两端的共同祖先仍可计算真实净增长。预算导致汇总上移时，按最终汇总范围判断。

目录体积同时对照卷可用空间。父子目录统计有重叠，汇总时选择一个层级；逻辑大小、实际分配空间、硬链接或共享存储的口径在报告中说明。收纳后的空间收益通过复测确认。

## 日志持续增长

先取得目录增量、写入来源、任务进展和少量近期日志，判断是正常批处理、重复报错、重试循环还是日志设置引起。采样覆盖需要回答的问题即可，巨型日志留在原位分析。

按本机约定使用程序支持的轮转、保留数量或日志级别设置，必要时修正增长来源。仍在写入的日志先核对程序的处理方式；旧日志按对应保留规则处理。操作后复测增长、服务功能和卷可用空间。当前工具 只报告线索，尚无自动日志修复能力。

## 按用途安排位置与保留

| 内容 | 处理方式 |
| --- | --- |
| 系统、应用、服务数据与依赖配置 | 留在所属软件要求的位置，使用其维护方式。 |
| 活跃项目和任务产物 | 留在项目或约定工作区，任务结束后再安排交付、归档或回收。 |
| 已结束项目中有价值的独立资料 | 收进约定归档位置，登记来源和去向，保持可查找。 |
| 重要冷数据、原始资料、用户交付物与指定恢复材料 | 按长期保留约定保护；`cold` 类别不可回收。 |
| 缓存、临时产物和普通日志 | 确认可重建条件、使用者及对应生命周期，再按已有规则维护。 |
| 用途未知的内容 | 原位保留，列出待查的归属、依赖和保留依据。 |

每个期限都应有具体起点，例如任务结束或日志轮转。工具当前的临时文件回收期限以修改时间计算；只有规则明确采用这一口径时才适用。访问时间、目录名称和文件年龄用作调查线索，回收依据来自已确认的用途与规则。

### 备份、缓存与数据库

备份按来源和恢复用途分组。采用“最近 3 份有效备份，加每个自然月 1 份归档”时，保留集合取并集，同时明确归档月数、容量上限和固定恢复点；增量备份保留完整依赖链。优先使用原备份工具的保留机制。规则缺项、集合超预算或恢复能力待验证时，列出需要补齐的事项。工具尚未计算或执行备份淘汰。

备份验证应说明实际完成了什么：副本检查、原件前后哈希核对和恢复演练分别验证不同目标。需要确认可恢复性时，安排对应的恢复演练。

缓存先确认重新取得的来源、离线需求、重建成本和共享使用者，再使用软件支持的接口。例如 uv 使用 `cache clean` / `cache prune`，实际行为按本机版本与[官方缓存说明](https://docs.astral.sh/uv/concepts/cache/)核对。原生清理可能直接删除数据，计划中写明重建条件与恢复限制。

SQLite WAL 属于数据库持久状态，应通过数据库支持的方式维护，并验证数据库健康与工作负载，参见 [SQLite WAL 说明](https://www.sqlite.org/wal.html)。回收站缺少原路径等元数据时，登记缺失的恢复线索，待规则与对象核实后再决定处置。

## 在特殊目录留下简短说明

自定义收纳目录、用途难以看出的目录和有特殊保留要求的目录，在约定允许时维护一份 `AGENTS.md`。只读接管阶段先登记说明缺口和拟写内容。说明放在需要解释的目录，不必逐层复制。

正文写用途、保留类别、规则来源和本机目录索引入口；有必要时补充内容边界、收纳去向和依赖，并标明哪些已确认、哪些待查。说明随用途和规则改变而更新，巡检流水另存状态。整份文件最多 8 KiB，保持短小并保护秘密。

`note` 生成以下成对标记区，保留区外的用户原文；已有旧标记或未知标记按原文保留。现有标记只有一端、重复或顺序错误时，先核对原文再处理。

```markdown
<!-- host-steward:begin -->
# 本目录用途与维护约定
<!-- host-steward:end -->
```

说明与规则冲突时，保留原文并暂停有争议的变更。说明的查找位置由 `status` 返回的 directory_index 提供；目录移动、用途改变或说明缺失时同步复核索引。

## 当前工具的回收范围

`note` 与 `quarantine` 默认预览，确认计划符合本机约定后才加 `--apply`：

```sh
python3 /skill目录/tools/steward.py note --state /本机状态 --path /约定目录
python3 /skill目录/tools/steward.py quarantine --state /本机状态 --path /约定临时文件
```

`quarantine` 只接收明确授权、满足期限的 temporary 普通文件，并核对目录身份和待回收区 `recycle_bytes` 预算。使用中的文件先处理使用关系；`AGENTS.md`、已在待回收区的对象和状态目录子树均不作为回收目标。

回收是同卷移动，记录原位置、目标位置、理由、时间与身份，释放空间记为 0。容量不足时暂停迁入，已有恢复期限继续有效。恢复和中断处理见 [恢复指导](recovery.md)。

### 最终删除另行决定

当前工具没有最终删除命令。首次部署尚未另作约定时，最终删除须逐项展示目标、理由、预期收益与恢复限制，等待用户确认。之后如有明确长期授权，也要按对应范围、额度和到期复查条件执行。

待回收区容量不足时，可依已有约定复查已到期对象；满足最终删除条件后才处置，保留其余对象的恢复期限。原生缓存清理同样使用其明确授权和原生接口，并在计划中说明直接删除的行为、重建条件与恢复限制。
