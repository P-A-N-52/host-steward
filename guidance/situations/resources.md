# 常驻程序与资源异常

资源异常先从主机正在做什么查起：读常驻约定，确认程序身份、任务进展和主要工作的影响，再与同一口径的历史样本比较。

## 让样本保持可比

进程以 `pid + started + executable` 识别。启动时间改变后，重新建立趋势，旧进程样本保留各自的生命周期。

CPU 结合持续时间、任务进展和前台体验判断。demo 的 `ps` 百分比采用进程 CPU 统计口径，整机当前负载需要结合其他指标解释。

内存结合实际压力和同一进程的多次样本判断。工具在 `current.json.samples` 保存有限 RSS 与 CPU 样本，agent 根据任务、缓存行为、持续时间和内存口径分析趋势，决定是否继续调查。需要跨轮跟进时按 [巡检指导](../patrol.md#待核验事项与记录收尾)登记事项。

每项指标保留来源、单位、时间口径和可用性。单位不明或与任务明显矛盾时，先标为待验证，补查后再用于计算或处置。

## 核对资源来自哪里

采样命令和短时前台任务单独辨认，避免将观察自身的消耗计作待清理负载。按可执行文件、启动时间和任务关系识别具体进程；解释器名称只能说明运行方式。

存储同时看目录增量和卷可用空间，父子目录的占用选择同一层级汇总，详细口径见 [文件与存储指导](files-storage.md)。GPU 利用率与模型费用当前标为未知，demo 尚无对应采样，也不调用需要提权的功耗采样。

## 先给主机让出资源

资源紧张时，先减少 Steward 自己的扫描、采样、并发和非必要分析。结合 CPU 核心数、内存余量、存储读写、电源状态与前台负载调整检查范围，在本机预算内优先保留关键检查和未完成操作的看护。

调整其他程序前，按 [巡检流程](../patrol.md) 核对允许动作、维护窗口和验证方法。demo 没有停止进程的命令。原因暂时查不清时，保存有限证据和下一步待查项，结束本轮调查。
