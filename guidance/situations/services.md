# 服务与后台任务异常

先把服务的稳定身份、常驻约定、实际配置和异常时间线对齐，再用所属程序的只读健康检查或实际功能确认影响。这样才能把“管理器中看到了服务”和“服务已能正常工作”分别说清楚。

## 服务清单与指定调查

当前工具有两种观察范围：

| 入口 | macOS | Linux |
| --- | --- | --- |
| `patrol` 服务清单 | 当前 launchd 域的标签 | systemd 系统管理器中正在运行的服务 |
| `inspect --service` | 指定 user（当前用户的 gui 域）或 system 域 | 指定 `--user` 或 `--system` 管理器 |

清单用于发现线索，其他域、停止状态和按需任务需要指定调查。定时或按需启动的服务当前没有 PID 时，结合调度与调用记录判断用途。

调查疑似遗留服务时，先按 [资源档案](../inventory.md) 读回用途与依赖，再查启动配置、主 PID 和 roots 内的引用。相对程序路径结合 WorkingDirectory 核对。磁盘上的配置与管理器当前生效状态分开记录：macOS 参见 [launchd 说明](https://github.com/apple-oss-distributions/launchd/blob/main/man/launchd.plist.5)，Linux 参见 [systemctl 手册](https://github.com/systemd/systemd/blob/main/man/systemctl.xml)。

近期错误只取必要样本，关联配置变化、资源压力、重启时间和依赖状态。报告采用元数据和必要摘要，环境变量值、认证配置与完整进程参数留在受保护的原始位置。

## 用证据缩小依赖范围

项目描述、低占用、近期无请求都能帮助选调查方向；备用服务和按需服务的正常状态也可能如此。静态引用调查的覆盖与限制见 [资源档案](../inventory.md)。进一步判断退役条件时，按相关性补查其他用户、子进程、历史调用及项目迁移记录。

调查结果保留目标身份、证据时间、已查范围、发现的引用、待查范围、拟议动作的影响和待决事项。结论明确适用于哪些范围，让下一轮可以接着查。

### 网络端点

`inspect` 只查看主 PID 的当前可见端点，最多展示 32 条，并报告截断和查询可用性。子进程、其他用户和历史调用另列待查。

回环监听说明观察时该端点直接绑定的地址。判断外部可达性时，还要检查相关转发与代理；判断服务功能时，使用实际客户端路径验证。

### 定时任务

核对调度时区、实际运行环境、调用分支和动作记录。任务退出后，直接检查预期目标是否达成，尤其留意脚本是否吞掉异常或跳过维护分支。

带精确分钟条件的脚本还要验证延迟触发能否执行。调整时区时分别确认实际执行时间和漏跑情况，保留下一次触发的核对依据。

## 恢复与退役

恢复服务前，把允许动作、影响范围、维护窗口、回退办法和功能验证写进具体计划，再按 [巡检流程](../patrol.md) 执行。保护对象出现高占用时，先调查任务与依赖，处置沿用其既有约定。demo 目前只观察服务，重启、安装和配置变更需使用另有授权的工具。

确认退役后，将停止、禁用、移除程序、移除数据分成独立动作，各自核对权限和影响；共享服务先确认其他用户与 agent 的依赖。所需决定尚未确定时，保留调查结果和待决事项。
